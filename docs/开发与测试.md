# 开发与测试

本地开发和自动测试命令在 GitHub 源码仓库根目录执行；部署包的 `source/` 不包含完整开发测试工具。服务器上的 2000 人彩排测试步骤见本文后半部分。

## 本地启动

使用 Node.js 24.14.1 或更新的 24.x。运行 `npm ci` 后执行 `npm run dev`。

启动器会创建本地 PostgreSQL、应用数据库迁移、构建 API 并启动前后端。默认端口为前端 5173、API 3000、数据库 55432；端口被占用时退出，不会停止其他进程。Linux 本地开发需使用普通用户运行，不能以 root 启动嵌入式 PostgreSQL。

开发启动先等待后端首次监听编译完成及接口就绪，再开放前端页面。后端仅在后续编译成功且运行代码内容确实变化时重启；文件时间戳变化、无内容变化的重新编译不会触发重启。编译报错时保留上一次正常运行的后端，修正错误并编译成功后再更新。修改依赖或环境配置后请手动重启开发环境。

需要更改端口或使用已有开发数据库时，复制 `.env.example` 为 `.env` 后修改。指定 `DATABASE_URL` 后会对该数据库执行迁移，请使用专用开发数据库。配置文件不能提交到 Git。

## 首次创建开发账号

保持 `npm run dev` 的终端开启，在项目根目录另开一个终端执行：

```sh
node --input-type=module -e "import {loadEnvironment} from './scripts/lib/config.mjs'; import {localSettings} from './scripts/lib/database.mjs'; import {spawnSync} from 'node:child_process'; loadEnvironment(); process.env.DATABASE_URL ||= (await localSettings()).connectionString; process.exitCode = spawnSync(process.execPath, ['scripts/account.mjs', 'init'], {stdio:'inherit', env:process.env}).status ?? 1;"
```

按提示设置账号和密码。密码输入不回显；不会输出数据库凭据。已有账号时不必初始化。开发库密码恢复可将上面命令中的 `'init'` 改为 `'reset-password'`。

生产安装和密码维护使用部署包的脚本，参见[部署说明](部署说明.md)，不要连接生产数据库进行开发测试。

## 数据与资源

- `.local/`：本地数据库、密钥及上传文件，仅在本机生成，不提交。
- `apps/api/build/`、`apps/web/build/`：构建输出，可重新生成，不提交。
- `artifacts/`：测试报告、隔离数据库、截图和打包结果，不提交。
- `apps/web/public/`：应用所需的默认 Logo、占位图和旧版兼容头像；运行时生成的模拟头像不在此目录，不提交。
- `.env.example`：无真实凭据的配置模板，可提交。

Ctrl+C 停止开发服务，已有数据保留。数据库迁移按顺序执行并检查校验值；已经应用的迁移不要修改，增加新的迁移文件。

## 验证

| 命令 | 检查内容 |
| --- | --- |
| `npm run check` | 工作区 TypeScript 和前端类型检查 |
| `npm test` | 正式系统单元测试 |
| `npm run build` | API 与前端生产构建 |
| `npm run test:deployment` | 安装、升级、备份、清理等部署脚本测试 |
| `npm run verify:draw` | 服务端开奖、补抽、并发与状态恢复 |
| `npm run test:soak-stage:smoke` | 大屏短时运行检查 |
| `npm run release:check` | 完整 13 项发布验收 |

集成测试创建隔离数据库和端口，不使用已有开发业务数据。微信测试使用模拟提供方，不能替代真实手机授权验收。

浏览器验证需要 Chrome；非默认安装位置可设置 `CHROME_PATH`。部署测试需要 Bash，当前 Windows 测试配置使用 `D:/Program Files/Git/bin/bash.exe`；其他安装位置需调整 `tests/deployment.test.mjs` 的 Bash 路径。Linux 使用 PATH 中的 `bash`。少数验证脚本以 Windows Chrome 路径为默认值，跨平台运行前应检查相应脚本的浏览器配置。

## 生成下一版部署包

```sh
npm run package:deploy -- --version=1.0.0-rc.3
```

替换为尚未发布的新版本号。脚本先完成发布验收，再生成压缩包和 SHA256。上传这两个文件及包内的 `INSTALLATION.md` 到 GitHub Releases；说明附件按包类型命名为 `SOURCE_INSTALLATION.md` 或 `IMAGES_INSTALLATION.md`。添加 `--images` 只生成镜像部署包；添加 `--both` 则在一次验收后同时生成源码和镜像部署包，保证两者源码一致。这两种选项需要构建机安装 Docker。仓库的 GitHub Actions 工作流默认同时构建并发布两种包，无需在本机安装 Docker。

部署文档只维护 `docs/部署说明.md`，打包时自动替换文中的示例包名，生成对应版本和类型的安装说明。包内不再附带重复的部署、清理及版本更新文档；`TESTING.md` 对应本文，包含开发说明和 2000 人服务器测试步骤。

版本更新内容填写在对应 GitHub Release 的正文中，不在源码中另存一份。Actions 发布时可填写本次更新摘要，并自动追加 GitHub 生成的变更记录。发布须使用新版本号，不覆盖历史压缩包；包内 `RELEASE.json` 继续保留验收信息。

## 模拟头像

每个模拟编号对应一张不同的 256×256 WebP 合成人物头像，最多 5000 张，无需外部图片服务。点击生成参与者后，服务器在后台按目标人数生成头像，最多同时编码两张；已生成的直接复用。首次进入大屏时可能仍在准备，按 H 查看进度。

生成文件保存到服务器运行目录的 `data/uploads/simulation/portraits-v1/`，本地开发默认是 `.local/uploads/simulation/portraits-v1/`（自定义 `ASSET_DIRECTORY` 时以其为准）。不同活动共享同编号的合成头像，不重复存储；删除活动不会删除这些可复用图片。源码仓库只保留生成代码，不附带这 5000 张图片。升级前已有的头像地址保持兼容，缺少缓存时按需补生成。已发布的历史部署包不受此次源码修改影响。

浏览器压力测试使用相同生成代码，在内存中构造独立头像，不再读取仓库静态图片。手工运行 `scripts/profile-matrix.mjs` 或 `scripts/verify-waterfall-startup.mjs` 前先执行 `npm run build`。可用 `npm run verify:rehearsal-seed` 验证完整生成流程。

## 2000 人服务器测试

适用于当前源码构建的部署包。新活动默认空彩排名单，支持按需生成不同头像的模拟参与者、每轮最多 10 人及头像本机缓存。

### 1. 安装或升级服务器

先按[部署说明](部署说明.md)或包内 `INSTALLATION.md` 完成安装或升级，确认网站可以登录。旧网站升级保留配置和业务数据；不要新建数据库或覆盖原网站目录。升级会短暂停止服务，请避开活动时间。

### 2. 生成 2000 名模拟参与者

1. 登录后台，创建一个专门用于测试的活动。
2. 保持彩排模式，进入「模式切换 → 模拟参与者」。
3. 在「模拟参与者总数」填写 **2000**，点击「生成模拟参与者」。
4. 新活动从空名单生成 2000 人；旧活动若已有 100 名模拟参与者，则只补充 1900 人。
5. 查看成功提示及当前模拟人数，再到「签到名单 → 彩排名单」检查总人数。

头像生成方式和保存位置见上方“模拟头像”。

可填 1–5000 的整数。重复填写同一个目标不会继续累加；不会删除已有人员、覆盖排除资格或重置中奖结果。若已有其他彩排签到人员，总签到人数可能大于 2000。

抽奖进行中、活动到期或已经启用正式模式时，不能生成模拟参与者。不要在活动进行中边抽奖边批量造数据。

如需减少人数，在「模式切换 → 清空彩排数据」清空后重新生成。此操作也会删除该场彩排的真实签到人员及抽奖记录，所以推荐使用专门的测试活动。只想重新抽奖则在中奖名单使用「清空抽奖」，保留已有参与者。

### 3. 检查完整业务流程

| 检查项 | 操作与预期 |
| --- | --- |
| 签到名单 | 显示 2000 人，翻页正常，搜索“模拟用户 2000”可找到完整编号 |
| Excel | 导出彩排名单，包含 2000 条人员记录（不含表头） |
| 大屏人数 | 进入彩排大屏，已签到人数与后台一致 |
| 头像轮换 | 同时显示的盒子数量保持各主题原设置，其他参与者通过轮换出现 |
| 真实抽奖池 | 未排除、未中奖的初始 2000 人均参与随机奖项的候选筛选，不限于当前显示的头像 |
| 多轮抽取 | 每轮最多 10 人，连续执行数轮，检查人数、剩余名额和名单保存 |
| 补抽 | 将一名中奖者标为不在场，执行补抽，确认作废与替代记录正确 |
| 清空抽奖 | 清空后大屏进度恢复，2000 人名单仍保留 |
| 清空彩排 | 清空后名单与抽奖记录为空，再次生成 2000 人正常 |
| 正式隔离 | 正式名单仍为空；模拟人员不会被复制到正式模式 |

在正式现场使用的电脑上分别检查梦幻星球、星光矩阵、星轨光波、星光长廊和星河瀑布。头像轮换需要时间，不会将 2000 个盒子一次性全部显示。

### 4. 记录服务器和浏览器表现

在服务器终端执行以下命令，每次执行一条；`starlit.sh` 命令须在原网站运行目录执行。分别记录待机、名单导出、开始/停止抽奖时的数据：

```bash
docker stats --no-stream
```

```bash
free -h
```

```bash
df -h /opt
```

```bash
bash starlit.sh status
```

```bash
bash starlit.sh logs
```

连续观察时运行 `docker stats`，按 Ctrl+C 结束观察。另记下：

- 服务器 CPU、内存与操作系统版本。
- 生成 2000 人、名单查询、导出和停止抽奖各耗时多久。
- 是否发生错误、超时、容器重启或内存持续增长。
- 现场电脑型号、浏览器、屏幕分辨率与各主题的流畅程度。

服务器 CPU 低不代表现场大屏一定流畅；3D 动画主要使用观众现场电脑的浏览器和显卡。

### 5. 这次测试覆盖什么

本功能生成的是实际保存到数据库的 2000 条彩排参与者记录，可检查名单、导出、抽奖、大屏数据和头像轮换。

**这不等于 2000 台手机同时扫码签到。** 新版使用 2000 张内容不同的合成头像，能够检查图片下载、解码、缓存和渲染；图片不是实际参与者的微信照片，不覆盖微信授权或集中签到请求。活动总人数也不等于瞬时并发人数，并发测试应按分批到场的扫码节奏单独设计，不能依据本次结果宣布服务器具备某一并发容量。

本地隔离 PostgreSQL/API 已测试 2000 条记录、完整 Excel 导出、2000 人抽奖池、权限与模式隔离；生产服务器表现以实际部署后的记录为准。
